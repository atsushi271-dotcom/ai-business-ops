# ケーススタディ：会話をまたいで判断の前提を保つ

## 背景

個人ECの運営で、事業上の事実、広告の指標、商品の表現方針、判断履歴をAIと扱っていました。
同じ前提の説明を繰り返すことや、未確認の情報が提案に混ざることが、運用上の課題でした。

## 整理した構造

1. 現在の事実・定義・決定・未解決事項について、参照する文書を決める。
2. SQL本体を文書から分け、文書には定義と索引を置く。
3. 過去のレビューを現在の事実の根拠として自動的に扱わない。
4. 決定には根拠と再開条件を付け、条件が変わった場合に見直す。
5. 文書更新の後に検査を実行する。

## 判断とトレードオフ

| 選択 | 狙い | 注意点 |
| --- | --- | --- |
| Markdownと小さなスクリプト | 人とAIが同じ情報を読み、差分を確認できる | 更新規律が必要 |
| テーマごとに正本を一つにする | 参照先を明確にする | 分けすぎると読解の負担が増える |
| 判断に再開条件を残す | 同じ話を繰り返さず、必要な変更には対応する | 条件の見直しは人が行う |
| 検査と事実確認を分ける | 自動で検査できる範囲を明確にする | 検査合格だけで業務上正しいとは言えない |

## 確認できる到達点

これは運用設計と成果物の実績です。継続利用の頻度や工数削減の定量効果は、この公開版では示していません。

公開版はその考え方を検証できる教材として再構成しました。実業務で使ったデータや全文書の複製ではありません。
